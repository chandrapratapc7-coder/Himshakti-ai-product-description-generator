## 📖 About

**HimShakti** is a Himalayan food processing brand based in Uttarakhand, producing millet snacks, pickles, jams, juices, and chutneys using traditional Pahadi recipes. Like most small food producers, writing polished, platform-specific product listings — the kind that actually convert on Amazon, Flipkart, or Instagram — takes marketing skill most small businesses don't have time to develop.

**HimShakti AI** solves this directly: enter a product's details once, choose a tone and target platforms, and get back a complete, ready-to-publish listing — title, short and long descriptions, bullet points, SEO keywords, and usage/storage guidance — generated by Google Gemini and tailored to each platform's conventions.

This project was built as a 10-week, full-stack, production-track internship under **TBI-GEU** (Technology Business Incubator, Graphic Era University), covering everything from initial scaffolding through to a live, publicly deployed application.

## ✨ Features

- 🤖 **AI-generated descriptions** — title, short/long description, bullet points, SEO keywords, and usage/storage notes, generated by Google Gemini with an automatic offline fallback if the API is ever unavailable
- 🎨 **Three writing tones** — Premium, Traditional, or Health-focused, each with distinct language and framing
- 📱 **Six target platforms** — Amazon, Flipkart, Meesho, Instagram, WhatsApp, and D2C, each with platform-specific copywriting conventions baked into the prompt
- 🖼️ **Product image upload** — attach a photo that appears in both the live listing preview and the saved listing card
- 💾 **Full CRUD on saved listings** — every generation is auto-saved to your account; search, edit, regenerate, or delete at any time, with confirmation before destructive actions
- 🔐 **Authentication** — email/password (JWT + bcrypt) or one-click Google OAuth
- 📊 **Usage dashboard** — charts showing generation activity by day, platform, tone, and category
- 🌙 **Dark mode** — a neutral, professional charcoal theme (not just a green tint) with green reserved for accents — active states, focus rings, and primary actions
- 📱 **Fully responsive** — verified at 375px, 768px, and 1440px breakpoints
- 🧯 **Resilient by design** — a global error boundary, distinct loading/empty/error states throughout, and rate limiting + input validation on every write endpoint

## 🛠️ Tech Stack

| Layer | Technology |
|---|---|
| **Frontend Framework** | React 18 + Vite |
| **Routing** | React Router v6 |
| **HTTP Client** | Axios (single shared instance, JWT auto-attached) |
| **Charts** | Recharts |

## 🏗️ Architecture

```
┌──────────────────┐        HTTPS / JSON        ┌──────────────────┐        ┌──────────────────┐
│   React + Vite     │ ─────────────────────────▶ │  Express REST API  │ ─────▶ │  MongoDB Atlas     │
│   (Vercel)          │ ◀───────────────────────── │  (Render)           │        │  (Cloud DB)         │
└──────────────────┘         JWT in header        └────────┬─────────┘        └──────────────────┘
                                                              │
                                                              ▼
                                                    ┌──────────────────┐
                                                    │  Google Gemini API │
                                                    │  (@google/genai)    │
                                                    └──────────────────┘
```

- **Frontend** is a client-side-routed SPA. All API calls go through a single shared Axios instance (`services/api.js`) which automatically attaches the current JWT to every request.
- **Backend** is a conventional layered Express API: `routes/` → `middleware/` (auth, rate limiting, validation) → `services/` (AI provider abstraction, prompt building) → `models/` (Mongoose schemas).
- **AI provider is abstracted** behind a single `generateDescription(input)` interface, so `AI_PROVIDER=gemini` or `AI_PROVIDER=openai` swaps the underlying implementation with no other code changes. If the live AI call fails for any reason, the backend transparently falls back to a local mock-content service rather than surfacing a hard error to the user.

## ⚙️ Getting Started

### Prerequisites
- Node.js v18+
- A [MongoDB Atlas](https://cloud.mongodb.com) account (free M0 tier is sufficient)
- A [Google Gemini API key](https://aistudio.google.com)
- (Optional) Google OAuth credentials, from [Google Cloud Console](https://console.cloud.google.com)

### Installation

```bash
git clone https://github.com/chandrapratapc7-coder/Himshakti-ai-product-description-generator.git
cd Himshakti-ai-product-description-generator

# Frontend
cd client
npm install

# Backend
cd ../server
npm install
```

## 🔑 Environment Variables

**`client/.env`**

| Variable | Description |
|---|---|
| `VITE_API_URL` | Base URL of the backend API (e.g. `http://localhost:5000/api` locally, or your live Render URL + `/api` in production) |

**`server/.env`**

| Variable | Description |
|---|---|
| `PORT` | Port the Express server listens on (default `5000`) |
| `MONGODB_URI` | MongoDB Atlas connection string |
| `JWT_SECRET` | Random secret string used to sign JWTs — generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `JWT_EXPIRES_IN` | How long a login session lasts (e.g. `7d`) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google OAuth credentials |
| `GOOGLE_CALLBACK_URL` | Full OAuth callback URL — must match what's registered in Google Cloud Console exactly |
| `CLIENT_URL` | The frontend's live URL, used for CORS (and by CORS only — do not confuse with the frontend's own `VITE_API_URL`) |
| `AI_PROVIDER` | `gemini` or `openai` |
| `GEMINI_API_KEY` | Google Gemini API key (required if `AI_PROVIDER=gemini`) |
| `OPENAI_API_KEY` | OpenAI API key (required if `AI_PROVIDER=openai`) |
| `AI_MODE` | Optional — set to `mock` to force offline mock content regardless of provider/key |

> ⚠️ Never commit `.env`. Verify it's ignored before every commit: `git check-ignore server/.env`

## 🗄️ Database Schema

```
User                              GeneratedDescription
├─ _id            ObjectId        ├─ _id              ObjectId
├─ name            String          ├─ user              ObjectId → User
├─ email           String          ├─ product           ObjectId → Product (optional)
├─ password        String (hashed) ├─ productName        String
├─ googleId        String (opt.)   ├─ category           String (enum)
└─ createdAt        Date           ├─ platform           [String] (enum)
                                    ├─ tone               String (enum)
                                    ├─ image              String (base64, optional)
                                    ├─ title / shortDescription / longDescription
                                    ├─ bulletPoints        [String]
                                    ├─ seoKeywords         [String]
                                    ├─ usageStorage        String
                                    └─ createdAt           Date
```

One `User` → many `GeneratedDescription` documents. `GeneratedDescription` (AI output) is intentionally separate from `Product` (an admin catalog) — the Saved Listings page reads from `GeneratedDescription`, not `Product`. Full reference: [`docs/database_schema.md`](./docs/database_schema.md)

## 🔐 Authentication

Two supported flows, both issuing the same JWT format used for every subsequent request:

- **Email/password** — bcrypt-hashed, rate-limited, validated
- **Google OAuth 2.0** via Passport.js — on first sign-in with a given email, if an account with that email already exists (e.g. from email/password registration), the Google account is **linked** to the existing user rather than creating a duplicate

Protected frontend routes (`/generator`, `/dashboard`, `/saved`) are gated behind a `ProtectedRoute` component that waits for the initial auth check to resolve before deciding whether to redirect — this avoids a race condition where a valid session could briefly look logged-out on page refresh.

## 🤖 AI Integration

Generation is handled by `services/geminiService.js`, which:
1. Builds a structured prompt (`promptBuilder.js`) incorporating the product details, selected tone, and platform-specific copywriting conventions
2. Calls Gemini with `responseMimeType: 'application/json'` to get a structured response directly
3. Falls back to a local mock-content service (`mockAiService.js`) if the live call fails for any reason — the user sees a toast noting offline content was used, but the request never hard-fails

> **A note on model pinning**: this project has been repeatedly affected by Google repointing the `-latest` model alias and fully deprecating older pinned models for newer API keys. The current implementation pins explicitly to a specific model version rather than an alias, and the reasoning is documented directly in `geminiService.js`. If generation starts unexpectedly falling back to mock content, check the backend logs for the exact Gemini error first — see [Troubleshooting](#-troubleshooting).

## ☁️ Deployment

Deployed as two separate services:

| Service | Platform | Root Directory |
|---|---|---|
| Frontend | [Vercel](https://vercel.com) | `client` |
| Backend | [Render](https://render.com) | `server` |
| Database | MongoDB Atlas | — (already cloud-hosted) |

**Key deployment notes:**
- `client/vercel.json` contains a catch-all rewrite rule (`/(.*) → /index.html`) — without this, direct navigation to any route other than `/`, or a page refresh on a deep route, returns Vercel's static-hosting 404 instead of letting React Router handle it.
- Backend environment variables are set directly in Render's dashboard, mirroring `server/.env`.
- `CLIENT_URL` on Render must match the live Vercel URL exactly (no trailing slash) for CORS to function.
- Google OAuth requires both `GOOGLE_CALLBACK_URL` (backend env var) and the corresponding entry in Google Cloud Console's **Authorized redirect URIs** to point at the live backend, not `localhost`.

## ⚠️ Known Limitations

- **Render free-tier cold starts** — the backend spins down after 15 minutes of inactivity; the first request afterward takes 30–60 seconds. Expected free-tier behaviour, not a bug.
- **Product images are stored as base64 directly in MongoDB documents**, not a dedicated file/image host. This is intentionally simple for the current scale, but means every Saved Listings page load transfers full image data even though only small thumbnails are displayed — a real performance cost as more image-attached listings accumulate. Migrating to Cloudinary/S3, or at minimum excluding the `image` field from the list query, is a planned improvement.
- **No automated test suite.** Testing has been manual and live throughout the project.

## 🩺 Troubleshooting

<details>
<summary><strong>Generation keeps falling back to mock content</strong></summary>

Check the backend logs for the line `AI generation failed, falling back to mock: <error>`. Common causes:
- `400 INVALID_ARGUMENT` — usually a mismatch between the pinned model version and its expected config shape (e.g. Gemini 3.x uses `thinkingLevel`, not the older `thinkingBudget`)
- `404 NOT_FOUND` — the pinned model has been deprecated for your API key; check Google's current model list
- `429` / `RESOURCE_EXHAUSTED` — rate limit hit, especially from rapid Regenerate clicks on a free-tier key
</details>

<details>
<summary><strong>"Request entity too large" on image upload</strong></summary>

Express's default JSON body limit is 100kb, which base64-encoded images easily exceed. Confirm `server.js` has `express.json({ limit: '10mb' })`, not the bare default.
</details>

<details>
<summary><strong>A route works locally but 404s after deploying (Vercel)</strong></summary>

Confirm `client/vercel.json` exists with the SPA rewrite rule, and that it was actually committed with valid, BOM-free JSON — a file created via a PowerShell redirect (`... | Out-File`) can silently include a byte-order-mark that makes Vercel reject it as invalid.
</details>

<details>
<summary><strong>"Cannot find module" on deploy, despite the file existing locally</strong></summary>

Almost always a filename casing mismatch. Windows filesystems are case-insensitive; Render and Vercel (Linux) are not. Verify the exact casing on GitHub's web UI, not just your local editor — a case-only rename doesn't always register as a real change to Git on Windows and may never have actually been pushed.
</details>
